# CI/CD

Всё описано в `.github/workflows/ci.yml` (GitHub Actions).

| Когда | Что происходит |
|---|---|
| Любой push и pull request | typecheck, `vitest` и `go test` хелпера на macOS, `go test` хелпера на Windows и Linux, проверка, что хелпер собирается под Windows |
| Push в `master`/`main` | то же + сборка `SenAWG-<версия>-setup.exe` (Windows), `.dmg` (macOS) и `SenAWG-<версия>-linux-x64.run` (Linux, только x64); файлы лежат в артефактах запуска 14 дней |
| Любой тег или опубликованный релиз GitHub | то же + загрузка установщиков на сервер, затем релиз на GitHub с `.exe`, `.dmg` и `.run` (без `SHA256SUMS`) |

## Выпуск версии

1. Поднять `version` в `package.json` (единственное место, где она задаётся) и закоммитить.
2. `git tag v0.5.2 && git push origin master v0.5.2` — или создать релиз во вкладке *Releases* на GitHub.

Папка на сервере называется по версии из `package.json`, а не по тегу. Если тег похож на версию (`v0.5.2`,
`0.5.2-beta`) и не совпадает с `package.json`, загрузка остановится с ошибкой: так забытое повышение версии не
перезапишет уже выпущенный релиз. Теги вроде `nightly` проходят и кладут сборку в папку текущей версии.

Релиз, созданный на GitHub вместе с новым тегом, запускает CI дважды (push тега и публикация релиза); второй запуск
отменяет первый, на сервер релиз попадает один раз.

Релиз на GitHub создаётся с заголовком `SenAWG <версия>` и описанием из коммитов с прошлого тега; тег с дефисом
(`v0.6.0-beta`) становится пре-релизом. Если релиз для тега уже опубликован вручную, в него только докладываются
файлы. Релиз, созданный самим CI, повторного запуска не вызывает — так устроен `GITHUB_TOKEN`.

## Сервер

На сервер попадает папка `<DEPLOY_PATH>/releases/<версия>/`:

```
releases/0.5.2/SenAWG-0.5.2-setup.exe
releases/0.5.2/SenAWG-0.5.2-setup.exe.sig
releases/0.5.2/SenAWG-0.5.2-arm64.dmg
releases/0.5.2/SenAWG-0.5.2-arm64.dmg.sig
releases/0.5.2/SenAWG-0.5.2-arm64.dmg.files.json       ← список файлов (ниже — «Обновление по частям»)
releases/0.5.2/SenAWG-0.5.2-arm64.dmg.files.json.sig
releases/0.5.2/SHA256SUMS
releases/blobs/<2 знака>/<sha256>.br                    ← общие для всех версий
```

Файлы сначала загружаются в `<версия>.partial`, а потом папка переименовывается одной командой, поэтому недокачанный релиз никто не увидит. На сервере нужны `rsync` и доступ по SSH-ключу.

Секреты — в *Settings → Environments → release* репозитория (окружение `release` можно закрыть ручным подтверждением):

| Секрет | Пример |
|---|---|
| `DEPLOY_HOST` | `vps.example.com` |
| `DEPLOY_USER` | `senawg` — отдельный пользователь без sudo |
| `DEPLOY_PORT` | `22` (необязательно) |
| `DEPLOY_PATH` | `/var/www/updates` |
| `DEPLOY_SSH_KEY` | приватный ключ, только для деплоя (ниже — как его получить) |
| `UPDATE_SIGNING_KEY` | ключ подписи обновлений (ниже — «Подпись обновлений») |

Ключ сервера не закреплён: раннер каждый раз новый и принимает тот ключ, что ответит первым
(`StrictHostKeyChecking=accept-new`), а остальные подключения той же выгрузки обязаны увидеть его же.
Украсть ключ выгрузки самозванец так не сможет — подпись SSH привязана к сессии, — а установщики и так
публичные. Теряется одно: уверенность, что релиз лёг именно на ваш сервер. Вернуть закрепление — секрет
с выводом `ssh-keyscan` в `~/.ssh/known_hosts` и `StrictHostKeyChecking=yes`.

### Ключ для выгрузки

1. На своём компьютере: `ssh-keygen -t ed25519 -f ~/.ssh/senawg-deploy -N '' -C 'github-actions senawg'`.
   Получатся `senawg-deploy` (приватный → секрет `DEPLOY_SSH_KEY`) и `senawg-deploy.pub` (публичный → сервер).
2. На сервере: пользователь без sudo и папка для релизов —
   `sudo adduser --disabled-password --gecos '' senawg`,
   `sudo mkdir -p /var/www/updates && sudo chown senawg /var/www/updates`.
3. Туда же публичный ключ — строка из `senawg-deploy.pub` в `/home/senawg/.ssh/authorized_keys`
   (папка `700`, файл `600`, владелец `senawg`).
4. Проверка: `ssh -i ~/.ssh/senawg-deploy senawg@<сервер> 'echo ok'`.
5. `pbcopy < ~/.ssh/senawg-deploy` и вставить в `DEPLOY_SSH_KEY` целиком, со строками `BEGIN`/`END`.

### Подпись обновлений

Приложение ставит обновление, только если рядом с установщиком лежит `<файл>.sig` — подпись Ed25519 над
системой, именем файла (в нём версия), размером и SHA-256 (`src/main/update/signature.ts`). Иначе скачанный
файл удаляется. Подписывает job выгрузки (`scripts/sign-update.mjs`) ключом из секрета `UPDATE_SIGNING_KEY`;
у сервера ключа нет, поэтому взломанный сервер может отдать любой файл, но не подписанный.

1. Ключ создаётся один раз: `node scripts/sign-update.mjs keygen <файл>`. Закрытая половина — в `<файл>`
   (права `600`), открытая печатается и вписывается в `UPDATE_KEYS`.
2. `gh secret set UPDATE_SIGNING_KEY --env release < <файл>` — или вставить содержимое файла в секрет вручную.
3. Сохранить копию `<файл>` офлайн. **Без него новые версии нечем подписать, и установленные копии перестанут
   обновляться.** Скрипт отказывается подписывать ключом, которого нет в `UPDATE_KEYS`.

Смена ключа: новый открытый ключ добавляется в `UPDATE_KEYS` рядом со старым, выходит версия с обоими, и только
потом секрет меняется на новый, а старый ключ убирается из `UPDATE_KEYS`.

### Обновление по частям

Установленная копия на Linux и macOS качает не весь установщик, а только изменившиеся файлы
(`src/main/update/files.ts`). Сборка (`scripts/make-delta.mjs`) описывает каждый файл того, что лежит в
установщике (`dist/linux-unpacked`, `dist/mac-arm64/SenAWG.app`), его SHA-256, и кладёт каждый файл
отдельным блобом brotli. Выгрузка подписывает список вместе с установщиками и докладывает блобы в
`releases/blobs/`, не трогая уже лежащие: неизменившийся файл — тот же блоб, поэтому новая версия обычно
добавляет на сервер и в загрузку пользователя лишь `app.asar` (сотни килобайт) и изменившиеся бинарники.

Приложение собирает новую версию во временной папке из своих файлов и скачанных блобов, сверяет её с
подписанным списком байт в байт и дальше ставит её так же, как распакованный установщик. При любой
неудаче — нет списка, не сошлась подпись, изменилась больше чем половина установщика (новый Electron),
не скачался блоб — качается весь установщик, как раньше. Версии до появления этого механизма о списках не
знают и обновляются целиком. Windows пока тоже обновляется целиком.

Блобы с сервера сами не удаляются. Чистить можно те, на которые не ссылается ни один `*.files.json`
оставленных версий.

## Чего пока нет

- **Linux.** Только x64: приложение спрашивает `GET /api/page/downloads/linux` и скачивает
  `SenAWG-<версия>-linux-x64.run`, который отдаёт сайт (`src/main/update/server.ts`); на другой архитектуре
  обновлений нет. Сборка ни разу не запускалась на настоящем Linux (`docs/linux.md`).
- **Подписи.** Сборки не подписаны (`identity: null` в `electron-builder.yml`): macOS покажет предупреждение Gatekeeper, Windows — SmartScreen.
- **DMG только под Apple Silicon** — раннер `macos-latest` arm64. `amneziawg-go` уже universal; для Intel-Mac нужен `--universal` у electron-builder.
  Поэтому и обновления на macOS — только на Apple Silicon.
- **Проверки подписи обновлений в версиях до 0.7.7 включительно.** Они ставят установщик, проверив только сайт,
  имя файла и первые байты; подпись (выше) проверяют версии после них.

## Обновление на macOS

Установщика нет — сайт отдаёт тот же `.dmg`, что перетаскивают в «Программы». Сделано по образцу Chrome
(Keystone и его relauncher) и Squirrel.Mac, без подписи и нотаризации (`src/main/update/mac.ts`):

1. «Перезапустить и обновить»: образ монтируется (`hdiutil attach -nobrowse`), приложение из него
   проверяется (id и версия в `Info.plist`) и копируется `ditto` рядом со старым — `.SenAWG-<версия>.app` в той
   же папке, на том же томе. Атрибут карантина снимается, хотя файл скачан самим приложением и его нет.
   Пока это идёт, приложение работает, на диске ничего из используемого не тронуто.
2. Запускается маленький скрипт и приложение закрывается. Скрипт ждёт закрытия не по pid (его может занять
   другой процесс), а по каналу: `cat` читает stdin, который держит приложение, и возвращается, когда оно
   вышло.
3. Два переименования: старое → `.SenAWG-old-<pid>.app`, новое → на его место; если второе не удалось,
   старое возвращается. Затем `open -n` открывает приложение с `--updated=<версия>`, положением окна и
   сервером, который был подключён. Новое окно встаёт на место старого, показывает «Обновлено до …» и
   подключается снова (на macOS — с вопросом пароля, как любое подключение). Если открылась старая копия
   (версия не та), она ничего не объявляет и пишет в журнал, что обновление не установилось.

Не обновляется копия, запущенная с образа или из «Загрузок» (App Translocation), и копия в папке, куда у
пользователя нет права записи (обычный пользователь, не администратор): в карточке обновления будет
объяснение, что сделать вручную. Из `npm run dev` установка не делается.

Посмотреть в браузере: `npm run demo`, затем `/demo/mac-update.html` (сам он открывает лабораторию интерфейса
`/demo/lab.html`, ссылка оттуда) — окно приложения на заглушке моста
(`src/renderer/src/demo/bridge.ts`, в сборку не попадает) и панель с шагами: проверка, загрузка, подготовка
рядом, закрытие окна, открытие новой копии на «Туннелях» с «Обновлено до …». Есть «Сразу к установке»,
скорость и вариант «Подмена не удалась». В самом Electron: `AWG_UPDATE_SIMULATE=available npm run dev` —
на macOS «Перезапустить и обновить» закрывает окно и открывает его снова на том же месте
(`AWG_UPDATE_DEMO=installer` — экран установщика Windows и Linux вместо этого).
